9. CrewAI and AutoGen

Stage 12 · Orchestration — two role-based multi-agent frameworks: one where you describe a team of specialists, one where agents talk to each other.

You'll be able to: build a small crew with roles and tasks, build an AutoGen conversation between agents, and decide whether either is a better fit than a graph.

Prerequisites: Multi-Agent · LangGraph · Graph Engineering

Why this exists

Both frameworks exist to make one thing easy: writing a multi-agent system as a description rather than as control flow. Instead of "call the researcher, then the writer, then check the writer's output", you write "here is a researcher, here is a writer, here is a fact-checker; do the task." The framework decides who speaks when.

That is genuinely pleasant for a prototype and genuinely risky for production, because "the framework decides who speaks when" means your control flow is now partly generated by a model. This file teaches both the pleasant part and the risk, and when to trade one for the other.

The mental model: CrewAI is a team with a manager and a task list; AutoGen is a group chat with a turn-taking rule.

The mental model

CrewAI  (role + task decomposition)          AutoGen  (conversation)

   manager / sequential                          agent A  ──► agent B
        |                                         ▲              │
   ┌────┴─────┬──────────┐                        └──────────────┘
 researcher  writer  reviewer                     messages carry the work;
        |         |        |                      a termination rule ends it
     task 1    task 2   task 3
        └────────► output ◄──────┘               control = who speaks next
   control = the task list you wrote

Both replace explicit edges with a policy. If you cannot draw your system as a graph afterwards, you do not understand it well enough to ship it.

Core concepts

CrewAI: agents with roles, tasks with expectations

An agent has a role, a goal and a backstory — prose that shapes its behaviour. A task has a description and an expected output, and can be assigned to an agent. A crew runs the tasks, either in order or under a manager agent that delegates.

from crewai import Agent, Task, Crew, Process

researcher = Agent(
    role="Policy Researcher",
    goal="Find the exact clauses that answer the question, with citations",
    backstory="You read dense policy documents and quote them precisely.",
    allow_delegation=False,
)

writer = Agent(
    role="Answer Writer",
    goal="Write a short answer that cites every claim",
    backstory="You never state a fact that is not in the provided sources.",
    allow_delegation=False,
)

find = Task(
    description="Find clauses answering: {question}. Return clause ids and quoted text.",
    expected_output="A list of clause ids with verbatim quotes",
    agent=researcher,
)

answer = Task(
    description="Using only the researcher's clauses, write a 120-word answer with citations.",
    expected_output="A short answer with inline [clause-id] citations",
    agent=writer,
)

crew = Crew(agents=[researcher, writer], tasks=[find, answer], process=Process.sequential)
result = crew.kickoff(inputs={"question": "What is the notice period for termination?"})

Notice what is doing the work: Process.sequential is the control flow, and it is one word. The moment you need "skip the researcher if the question is about pricing", you are back to conditionals — which is the honest signal that you wanted a graph.

AutoGen: agents as conversational participants

AutoGen models a conversation. Each agent receives messages and decides whether to reply, call a tool, or hand over. Termination comes from a rule (max_turns, a sentinel string, or an explicit check function) — and getting that rule right is most of the engineering.

import autogen

config = {"config_list": [{"model": "gpt-4o-mini", "api_key": "..."}]}  # use env vars, not literals

planner = autogen.AssistantAgent(
    name="planner",
    llm_config=config,
    system_message="Break the request into numbered steps. Do not write code.",
)
engineer = autogen.AssistantAgent(
    name="engineer",
    llm_config=config,
    system_message="Implement the plan. Reply TERMINATE when the code runs.",
)
critic = autogen.AssistantAgent(
    name="critic",
    llm_config=config,
    system_message="Find one concrete bug or gap per reply. Reply TERMINATE if none.",
)
executor = autogen.UserProxyAgent(
    name="executor",
    human_input_mode="NEVER",
    code_execution_config={"work_dir": "sandbox", "use_docker": True},
    is_termination_msg=lambda m: "TERMINATE" in (m.get("content") or ""),
)

group = autogen.GroupChat(agents=[planner, engineer, critic, executor], messages=[], max_round=12)
manager = autogen.GroupChatManager(groupchat=group, llm_config=config)
executor.initiate_chat(manager, message="Add pagination to the /orders endpoint and test it.")

max_round=12 is not a formality. Conversational multi-agent systems are the easiest place in this whole roadmap to burn money in a loop: two agents politely agreeing with each other for forty turns. Always set a hard round limit and always log every message.

The honest comparison

Dimension CrewAI AutoGen A LangGraph A plain loop
Control flow Task list, optionally manager-led Model-decided turn taking You write the edges You write the code
Debuggability Medium — task boundaries help Low — emergent conversations High — inspect state per node Highest
Cost predictability Medium Low High High
Best at Repeatable pipelines with clear roles Research, debate, code review loops Anything with real branching or approval Anything under ~3 steps
Worst at Branching Budgets and termination Prototyping speed Multi-role orchestration

When role-play helps and when it is theatre

Giving a model a role does change behaviour, mildly, because the role text is context. Two things follow. First, roles are a cheap way to get different attention — a critic that is told to find bugs finds more bugs than a writer asked to check its own work. Second, roles do not add capability — a "Senior Staff Engineer" persona does not know more than the same model without the persona, and any framework selling you capability through job titles is selling you a costume.

The test that keeps you honest: remove the role prose and see whether quality drops. If it does not, delete the prose and keep the pipeline.

Code

A CrewAI crew whose output you can actually evaluate — the part most examples skip.

from __future__ import annotations

import json
import re
from crewai import Agent, Crew, Process, Task


def build_crew() -> Crew:
    extractor = Agent(
        role="Extractor",
        goal="Return structured fields, never prose",
        backstory="You output JSON only.",
        allow_delegation=False,
        verbose=False,
    )
    checker = Agent(
        role="Checker",
        goal="Reject any field not present verbatim in the source",
        backstory="You are strict about evidence.",
        allow_delegation=False,
        verbose=False,
    )

    extract = Task(
        description=(
            "From the invoice text, extract vendor, invoice_number, total, currency. "
            "Return JSON with exactly those four keys.\n\nTEXT:\n{text}"
        ),
        expected_output="A JSON object with four keys",
        agent=extractor,
    )
    verify = Task(
        description=(
            "Check the extractor's JSON against the source text. For each field, mark "
            "supported true or false. Return JSON: {fields: {...}, all_supported: bool}"
        ),
        expected_output="JSON verdict object",
        agent=checker,
    )

    return Crew(agents=[extractor, checker], tasks=[extract, verify], process=Process.sequential)


def run(text: str) -> dict:
    result = build_crew().kickoff(inputs={"text": text})
    raw = str(result)
    match = re.search(r"\{.*\}", raw, re.DOTALL)     # crews often wrap JSON in prose
    if not match:
        return {"ok": False, "reason": "no json in output", "raw": raw[:400]}
    try:
        verdict = json.loads(match.group(0))
    except json.JSONDecodeError:
        return {"ok": False, "reason": "unparseable json", "raw": raw[:400]}
    return {"ok": bool(verdict.get("all_supported")), "verdict": verdict}

The lesson in that snippet is the re.search and the two failure returns. Framework output is prose until you make it not be; every framework boundary needs a parser and a failure path, or your pipeline will happily pass a string where a dict belongs.

TypeScript: the practical pattern is to keep CrewAI/AutoGen on the Python side and expose the crew behind an HTTP endpoint.

type CrewResult = { ok: boolean; verdict?: Record<string, unknown>; reason?: string };

export async function runCrew(text: string): Promise<CrewResult> {
  const res = await fetch(`${process.env.CREW_URL}/run`, {
    method: "POST",
    headers: { "content-type": "application/json" },
    body: JSON.stringify({ text }),
    signal: AbortSignal.timeout(60_000),
  });
  if (!res.ok) return { ok: false, reason: `crew http ${res.status}` };
  return (await res.json()) as CrewResult;
}

Real use case

A consultancy builds a bid-response assistant. A crew of four — requirements extractor, evidence finder, drafter, compliance checker — produces first drafts of tender responses from a library of past bids. It works well enough to demo, and the team ships it to two pilot users.

Two weeks later the complaint is not quality, it is variability: the same tender produces different structure on different runs, because the manager agent occasionally reorders tasks or asks the checker to also draft. The team's fix is not a better prompt; it is to freeze the pipeline — the four steps become four nodes in a graph with fixed order, the checker keeps its role prose (it demonstrably catches more), and the manager agent is deleted. Cost per run drops by roughly a fifth and the output variance complaint disappears.

The generalisable part: role-based frameworks are excellent at discovering the decomposition, and graphs are better at executing it repeatably. Prototype in the framework, then pin the graph.

Common mistakes

  • Mistake: no hard turn or round limit — Instead: set max_round, max_turns or a step budget on every multi-agent run, and log the count per request.
  • Mistake: agents that can all talk to all agents about anything — Instead: give each agent the smallest context it needs; broadcast-everything is how conversations balloon.
  • Mistake: trusting role prose as a safety control ("you are a careful agent") — Instead: enforce with code: allowlisted tools, validated output, approval gates.
  • Mistake: parsing framework prose with json.loads and no fallback — Instead: extract the JSON substring, and return a typed failure when it is absent.
  • Mistake: adding agents to fix a quality problem — Instead: add an eval first; usually the fix is better retrieval or a stricter output contract, not a fifth persona.
  • Mistake: assuming the manager agent's delegation is deterministic — Instead: if the order matters, encode it; if it does not, say so in the README and bound the cost.

Checkpoint

  1. Build the two-agent invoice crew above and run it on three real invoices. Count how often the JSON needs the regex fallback.
  2. Rebuild the same pipeline as a LangGraph with fixed nodes and no manager. Compare cost, latency and output consistency across five runs.
  3. Add a hard round limit and a per-run token budget to an AutoGen conversation, then deliberately give it an impossible task and confirm it terminates instead of looping.

Self-check: if removing the role/backstory text does not change your output quality on a blind comparison, delete it — you were paying tokens for a costume.
